# EC2 SSM 자동 배포와 실제 화면 증빙 설계

## 승인된 의도와 범위

사용자는 2026-11-07 기존 EC2를 켜고 SSM 방식으로 자동 배포를 구현·실제 검증하며 README용 실제 화면 GIF를 만들도록 요청했다. 앞서 합의한 CI 커버리지·차단·이미지 동일성 계약을 유지한다. 운영/배포 승인자는 임익현이며 배포 가능 시간은 한국 시간 09:00 이상 18:00 미만이다. 적용 요일은 제한하지 않는다(구현 제안).

## 대안과 선택

- SSM: SSH 키를 GitHub에 보관하지 않고 OIDC 임시 자격 증명과 대상 제한 원격 명령을 사용한다. Agent와 인스턴스 프로파일 준비가 필요하다. 사용자가 선택했다.
- SSH: 부트스트랩은 쉬울 수 있지만 개인 키·host key 관리가 추가된다. 상시 CD 경로로 사용하지 않는다.
- CodeDeploy/ALB blue-green: 현재 단일 t3.small·기존 Nginx/Compose 구조보다 범위·비용이 커 이번에는 도입하지 않는다.

## 대상과 변경 경계

- AWS 909345918351 / ap-northeast-2 / dev-stud-server / i-0bedbcc72c616cdb1.
- 기존 인스턴스 역할 ec2-ecr-read에 AmazonSSMManagedInstanceCore 연결은 적용 직전 별도 승인받았다. 기존 ECR 권한은 유지한다.
- 이미지 게시 역할 SeoulWave-CI는 유지하고, 원격 배포 권한은 별도 SeoulWave-Deploy 역할로 분리한다. 실제 권한 생성 직전에 별도 확인받는다.
- 개발 도중 서버의 현재 파일·컨테이너·데이터·Nginx·공개 IP를 먼저 조사한다. 기존 .env.prod 및 데이터 볼륨을 덮어쓰지 않는다. 첫 설치가 필요하면 일회성 준비와 반복 자동 배포를 구분한다.
- DB 마이그레이션·초기화·장소 데이터 적재·관리자 서비스 갱신은 자동 배포에서 제외한다. 필요한 경우 별도 승인 작업으로 다룬다.

## 자동 배포 구조

1. 기존 Verified application pipeline 성공 완료 후 별도 workflow_run CD가 dev push의 성공 실행만 허용한다. PR·취소·실패·다른 저장소·다른 workflow를 거부한다.
2. 원본 실행 ID의 verified-release를 다운로드해 source SHA·run ID·필수 검사·두 저장소의 digest 참조·config ID를 검사한다. artifact SHA-256도 검증한다.
3. 한국 시간 09:00~18:00만 배포한다. 허용 시간 밖에는 배포를 차단하고 이유를 알린다. 대기열/예약 재실행은 이번 범위 밖이다.
   - 정책 판단: 신뢰된 `dev` push 파이프라인의 성공 자체가 배포 승인이다. 매 실행마다 별도 수동 승인을 요구하지 않는다.
   - 허용 시간은 배포 접수(admission) 기준이다. 18:00 전에 시작한 SSM 배포는 서비스가 일관된 상태가 되도록 검사·롤백까지 계속할 수 있다.
   - 요일 제한은 두지 않는다. 사용자가 시간대만 지정했고, 추가 휴일 달력은 요청하지 않았다.
4. 배포별 전역 동시성 잠금은 cancel-in-progress=false로 두어 진행 중인 원격 변경을 취소하지 않는다. 서버에서도 파일 잠금으로 중복 실행을 막는다.
5. 이름이 `SeoulWave-Deploy-v1`인 SSM 전용 문서는 고정된 root 소유 배포 도구만 실행한다. 디스패처는 문서 버전 1을 지정한다. 허용 파라미터는 source SHA, 원본 run ID, backend/frontend config ID와 고정 두 ECR 저장소의 digest 참조다. 임의 shell 명령·임의 URL·배포 경로를 파라미터로 받지 않는다. 새 실행 콘텐츠는 새 문서 이름으로 만들어 IAM 경계를 유지한다.
6. 서버의 기존 Compose/운영 설정을 사용해 backend, frontend, itinerary-worker, database-health-monitor만 갱신한다. db와 관리자 서비스는 갱신하지 않는다. DB가 준비되지 않았거나 새 migration이 필요하면 배포를 중단한다.
7. 이미지 config ID와 digest 참조, Compose 준비 상태, 프록시 health, 비인증 API의 401을 확인한다. 기존 운영 로그인 정보가 서버에 있으면 외부 LLM 없이 로그인·시간표 조회도 확인한다. 이 마지막 확인은 Secure 쿠키 특성을 유지하면서 고정 loopback 연결에서만 수행한다. 명령/알림/Artifact에 비밀값을 출력하지 않는다.
8. 갱신 전 이미지 참조를 보존한다. 변경 후 검사 실패 시 이전 참조로 네 앱 서비스를 복구하고 복구 검사 결과를 남긴 뒤 CD를 실패 처리한다. DB 스키마는 건드리지 않아 이미지 롤백과 DB 되돌림을 혼동하지 않는다. 복구 실패도 성공으로 처리하지 않는다.
9. 성공 시 현재·이전 릴리스를 하나의 `release-state.json`으로 원자 기록한다. 미변경 거부·preflight 실패는 `not_applied`, 교체 실패 후 복구는 `rolled_back`, 복구도 실패하면 `rollback_failed`로 구분한다. SSM 명령 결과를 기다려 원격 성공까지 확인하고 Discord에 실제 배포 성공/실패를 알린다.

## 테스트 경계(사용자 승인)

- 배포 요청 공개 인터페이스: 신뢰된 원본 실행·검증된 릴리스·정확한 저장소·시간·대상을 허용/거부하는 결과를 검사한다. 실제 AWS 자격 증명은 검사하지 않는다.
- 서버 배포 CLI: 파일 잠금·변경 전 검사·상태 실패 시 롤백·복구 실패 결과를 외부 명령 경계에서 모의 Docker로 검사한다. 실제 운영 건강 상태는 대체하지 않는다.
- 실제 배포: GitHub 원본 실행→SSM→EC2 실행 digest/config ID→실제 HTTP·브라우저 화면까지 대조한다. 실제 LLM 추천·관리자 서비스 전체 E2E를 검증했다고 확대하지 않는다.

## GIF 증빙

합성/재현 UI를 만들지 않고 실제 Actions·서비스 브라우저 화면만 캡처한다. 짧은 단계 캡처를 시간 압축한 GIF임을 명시한다. IAM·SSM 원문 출력·계정 메뉴·키·비밀번호·사용자 데이터는 공개하지 않는다. README에는 실행 링크와 검증 범위, 이미지와 함께 실제 배포 시점을 기록한다. 성공한 배포가 없으면 성공 GIF를 만들지 않는다.

## 미해결 전제 및 실패 방침

2026-11-07 사용자 제공 read-only SSM 결과로 Ping online, 기존 사용자·관리자·PostgreSQL 컨테이너, Compose 파일 경로, `.env.prod` 존재(내용은 읽지 않음), 두 데이터 volume, pending migrations `none`, Nginx :80, app loopback :8080/:8081, 가용 메모리 1.2 GiB와 디스크 24 GiB free를 확인했다. 앱·관리자·DB·Nginx·데이터는 사전 승인 없이 변경하지 않는다. 현재 public IPv4/DNS는 확인 전이며 실제 HTTP 검증 전에 확인한다. 필요한 비밀값이나 일회성 초기화 승인이 없으면 실제 배포 완료를 주장하지 않는다. 서버를 임의 중지하지 않으며 작업 종료 시 실행 상태와 잔여 비용을 보고한다. 15분 미응답 에스컬레이션과 오토힐링은 이번 자동 배포 구현 범위 밖이다.
