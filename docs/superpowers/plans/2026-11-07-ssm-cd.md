# EC2 SSM CD Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 성공한 CI의 동일 이미지를 EC2에 자동 배포하고 실제 화면 GIF로 검증 결과를 보관한다.

**Architecture:** workflow_run CD가 신뢰된 verified-release만 받아 OIDC와 전용 SSM 문서로 배포한다. 서버의 고정 도구가 Compose 앱 서비스만 변경하며 잠금·preflight·digest/config·HTTP 검증·이미지 롤백을 수행한다.

**Tech Stack:** Python 3 stdlib, GitHub Actions, AWS OIDC/SSM, Docker Compose, Nginx, 실제 브라우저 캡처/GIF 인코딩.

**Spec:** docs/superpowers/specs/2026-11-07-ssm-cd-design.md

## Global Constraints

- 대상 i-0bedbcc72c616cdb1 / ap-northeast-2만 허용.
- 한국 시간 09:00 이상 18:00 미만에만 배포.
- DB 마이그레이션·초기화·데이터 적재·관리자 서비스 변경은 자동으로 수행하지 않음.
- 운영 .env.prod·DB 볼륨·호스트 Nginx 보존; 전체 compose config 출력 금지.
- 테스트 이미지 재빌드 금지; ECR 참조는 두 고정 저장소의 @sha256만 사용.
- EC2 상태·서버 설정을 조사하기 전 신규 설치로 가정하지 않음.

## Review Focus

- 원본 실행과 다른 Artifact·커밋·저장소를 거부해야 한다.
- 뒤늦게 완료된 이전 커밋이 최신 배포를 덮지 않아야 한다.
- 시간 밖·중복 실행은 앱 변경 전에 차단해야 한다.
- 상태 검사 실패/복구 실패/네트워크 지연을 성공으로 숨기지 않아야 한다.
- 비밀값과 관리 화면이 공개 GIF·로그·Artifact에 노출되면 안 된다.

Task 2 implementation note: the fixed host runner, SSM document `SeoulWave-Deploy-v1`, OIDC trust/permission policy, and contract tests are committed. With the user's explicit approval, AWS role `SeoulWave-Deploy`, its single inline policy `SeoulWave-Deploy-SSM-v1`, and SSM document version 1 were created. Readback matched the local trust and document JSON; the inline policy contains only `ssm:SendCommand` scoped to the fixed document and EC2 plus `ssm:GetCommandInvocation` for polling. Dispatch must name document version 1. Non-mutating rejection, lock conflict, and preflight failure use the additional outcome `not_applied`; this keeps them distinct from a rollback after a service change.

## 실행 방식과 점검

사용자가 승인한 격리 worktree에서 `executing-plans`를 따라 직접 구현한다. 실행 스킬은 설치되어 사용할 수 있다. 설계와 이 계획은 앞선 지시로 이미 승인되어 재확인을 요구하지 않는다. IAM 역할·신뢰 정책·SSM 문서는 승인된 범위로 생성 및 검증했다. GitHub 공유 브랜치 push와 실제 서비스 배포는 각 외부 변경 경계에서 별도 실행 승인을 받는다.
