## 1. 서비스 개요와 문서 안내

### 1.1 서비스 정의

한강버스 이용자가 **출발 선착장과 도착 선착장**, 출발 희망 시간, 동행 유형, 선호 활동을 선택하면, 한강버스 운항정보와 서울시 문화행사 정보를 결합하여 **실행 가능한 AI 나들이 코스 1개**를 추천하는 비회원 서비스다. 결과에는 이동·행사·산책 등 일정 순서, 추천 이유, 근거, 지도 위치와 공유/저장 기능을 제공한다.

### 1.2 이용 흐름

1. 출발 선착장과 도착 선착장을 각각 선택한다. 유효한 운항 방향·지원 구간만 허용한다.
2. 출발 희망 시간, 동행 유형(가족/연인/친구/혼자), 선호 활동(전시·공연/문화행사/산책·힐링/맛집·카페)을 선택한다.
3. **여행 가능 시간·총시간 예산 입력은 제공하지 않는다.** 선택한 시간은 실제 배편 출항 확정 시각이 아닌 희망 시간이다.
4. 시스템이 검증된 운항·행사·이동 데이터를 토대로 **추천 코스 1개**를 만든다. 데이터가 불충분하면 사실처럼 꾸미지 않고 미확인 또는 추천 불가로 안내한다.
5. 결과 화면에서 타임라인, 장소, Kakao 지도(연동 가능 시), 추천 이유, 운항/행사 출처를 확인한다.
6. 마음에 들지 않으면 **사용자 재생성 최대 2회**를 실행한다(최초 1회 + 재생성 2회 = 최대 3개 버전). 재생성은 같은 입력 조건을 유지하고 이전 결과와 차별화된 검증 후보를 우선한다.
7. 회원가입 없이 **공유 링크**, **PDF 다운로드**로 마음에 드는 결과를 보관한다. 브라우저 공유 기능을 지원하면 Web Share API도 사용한다.

### 1.4 데이터 신뢰성

서울시 문화행사 API는 행사 기간과 장소를 제공하더라도 특정 날짜의 입장 가능 여부·예약 잔여석·당일 취소를 보장하지 않는다. 행사 원문·갱신 시각·공식 링크를 보존한다. 지도상 직선거리나 추정 경로를 실제 도보 경로로 단정하지 않는다. 실제 운항 확인이 안 된 일정은 '예시/확인 필요'로 표시하며 확정된 일정으로 공개하지 않는다.

## 2. 제품 목적과 성공 조건

### 2.1 해결할 문제

선착장 주변 행사 목록만 제공하면 기존 지도·문화포털과 차별성이 약하다. 이 서비스는 **한강버스를 타고 어느 선착장에서 내려 어떤 문화활동을 어떤 순서로 즐길지**를 하나의 실행 가능한 일정으로 구성해 탐색 부담을 줄인다.

### 2.2 사용자와 핵심 결과

- 일반 사용자: 비회원으로 선착장·출발 희망 시각·동행·활동을 선택하고, 추천 코스 1개를 확인한 뒤 최대 2회 재생성하거나 공유·PDF 저장한다.
- 운영자: 기존 인증된 운영 화면에서 수집, 실행, 재생성, 장애 및 복구 상태를 조회한다.
- 평가자: 기존 필수 멀티 에이전트 협업, Critic 검증, FT-01~04, Compose/CI/CD/알림의 실증을 확인한다.

성공 조건: 입력한 출발/도착 방향이 유지되고, 허위 행사나 가상 운항시간을 생성하지 않으며, 결과 1개·재생성 상한·공유/PDF 출력이 검증되고, 기존 과제의 운영·장애 요건을 충족한다. 측정 전 수치는 실적이라고 주장하지 않는다.

## 3.3 v1.1 제품 변경 우선 적용 계약

**문서 적용 우선순위:** 이 3.3절과 4.0절 및 5.0절의 v1.1 변경 요구는 뒤에 보존된 v1.0의 상충하는 제품 규칙보다 우선한다. 뒤쪽의 기존 운영·보안·복구·시험 기준은 충돌하지 않는 범위에서 승계한다. 특히 '총시간 입력', '취향 입력 없음', '결과 최대 3개', '전시 카드 3개 비교', '재생성 없음', '코스 테이블 불필요'는 폐기한다. 기존의 검수 후보 풀 최대 3개는 초기 운영 데이터 제한으로 유지할 수 있지만 **화면 출력은 항상 코스 1개**다.

### 3.3.1 입력·코스 생성

- `origin_stop_id`와 `destination_stop_id`는 필수이며 서로 달라야 한다. 실제 지원되는 운항 방향만 허용한다. 선택값에 따라 가능한 도착 선착장과 출발 회차를 갱신한다.
- `preferred_departure_time`은 필수 희망 시각이며, 당일 아직 출발하지 않은 검증된 회차를 선택·안내한다. 사용자 동의 없이 출발·도착지를 바꾸지 않는다.
- `companion_type`은 `family | couple | friends | solo`; `activity_type`은 `exhibition_performance | culture_event | walk_healing | food_cafe`로 정의한다. UI 문구는 한국어로 표시한다.
- 총시간/종료 시각 입력이 없으므로 **4시간 코스라고 고정 표시하지 않는다.** 실제 산출된 일정의 예상 시작·종료와 총소요시간을 결과에서 계산해 표시한다. 관람·이동 소요시간이 검증되지 않으면 총소요시간은 미확인으로 표시한다.
- 행사·운항·이동의 필수 정보가 검증되지 않은 경우 해당 단계를 확정 일정으로 추천하지 않는다. 선택 활동에 맞는 검증된 후보가 없으면 '적합한 코스를 생성할 수 없음'과 사유를 제공한다.

### 3.3.2 단일 결과와 재생성

- 최초 생성은 `generation_index=0`; 사용자 재생성은 `1`, `2`까지 허용한다. 결과 화면은 **현재 선택된 버전 1개만** 표시한다.
- 같은 입력/동일 비회원 세션의 `itinerary_group_id`에 재생성 횟수를 저장하고 DB 트랜잭션으로 상한을 강제한다. 브라우저 새로고침, 다중 탭, 중복 클릭으로 횟수가 초기화되거나 초과되지 않게 한다.
- 내부 LLM/API 일시 오류 재시도, Critic 수정 루프, 업무 후보 재탐색은 **사용자 재생성 2회에 포함하지 않는다**. 반대로 사용자가 명시적으로 재생성을 누른 성공 요청은 별도 버전으로 기록한다.
- 재생성 시 이전 추천의 행사·경로를 참조하여 가능한 한 다른 적격 조합을 우선한다. 새로운 검증 조합이 없으면 **횟수를 소비하지 않고** '다른 검증 코스 없음'을 안내한다. 결과가 달라질 것을 보장하지 않는다.
- 추천 조건을 수정하면 새로운 그룹의 최초 생성으로 취급한다. 비회원 제한은 동일 세션/그룹 범위이며 계정 단위 악용 방지 보장은 하지 않는다.

### 3.3.3 공유·PDF

- **공유 링크:** `POST /api/itineraries/{id}/share`로 현재 버전의 읽기 전용 스냅샷을 만들고, 무작위 추측이 어려운 토큰 기반 `/share/{token}` URL을 발급한다. 링크는 로그인 없이 조회 가능하며 수정·재생성·운영 로그 접근 권한을 부여하지 않는다.
- 공유 토큰의 만료·철회 정책은 팀 결정 필요. 기본 제안은 **7일 만료**, 서버에는 토큰 해시만 저장, 개인정보/세션 식별자는 공유 응답에서 제거. 공유 링크는 전달받은 누구나 볼 수 있음을 UI에 고지한다.
- **PDF 다운로드:** `GET /api/itineraries/{id}/pdf` 또는 검증된 공유 스냅샷의 PDF를 생성한다. 제목·선착장·일정·행사명·장소·출처·조회 시각·확인 필요 문구를 포함한다. 지도 이미지는 Kakao의 이용약관/정적 지도 사용 권한 확인 후 포함하고, 불가하면 장소명·주소·지도 링크를 넣는다.
- 브라우저가 지원하면 Web Share API로 공유하고, 미지원 시 링크 복사로 대체한다. 비회원 소유권은 원본 편집/재생성/PDF 요청에 검증하며 공유 URL의 읽기 전용 공개와 구분한다.

### 3.3.4 지도 및 행사 API

- 서울열린데이터광장 **서울시 문화행사 정보 API**를 기존 일일 09:00 수집 파이프라인에 연결한다. 원본 필드, 중복, 좌표, 시간, 종료/취소 상태를 검증한다. 전시뿐 아니라 공연·축제 등 카테고리를 취향과 연결한다.
- Kakao Maps JavaScript SDK에서 출발·도착 선착장과 코스 장소를 마커/순서로 표시한다. 경로선은 **검증된 경로 좌표가 있을 때만** 사용한다. Kakao 지도 SDK만으로 보행 경로/시간이 자동 제공된다고 가정하지 않는다. 필요한 길찾기/이동시간은 별도 사용 가능한 API 또는 검수 데이터로 계산한다.
- Kakao 앱 키·허용 도메인·호출 한도·약관을 확인한다. 지도 로드 실패 시 텍스트 일정과 주소·외부 지도 링크로 대체하며 코스 자체를 숨기지 않는다.

### 5.0.2 DB 확장 초안

- `itinerary_groups`: 그룹 ID, 비회원 세션 식별자 해시, 출발/도착, 희망 시각, 동행/활동, `regeneration_count`(0~2), 생성·만료 시각.
- `itinerary_versions`: 그룹 ID, 버전(0~2), 실행 ID, 코스 JSON, 사용한 행사/시간표 스냅샷 ID, 검증 상태, 생성 시각. `(group_id, version)` 유니크.

## 4. 사용자 흐름과 수용 기준 (v1.0 보존 참고: 상충 시 4.0 우선)

### 4.1 정상 화면 흐름

1. 클릭 노선도에서 검수된 출발→도착 구간 1개를 선택한다. 미지원 구간은 차단한다.
2. 조회일은 서버의 Asia/Seoul 오늘로 표시한다. 오늘 아직 출발하지 않은 회차를 선택하고 출처·계산 도착예정을 확인한다.
3. 선택적으로 배 출발부터의 총시간을 입력한다. 취향·무료 여부·자유문 선호 입력은 없다.
4. 서버는 최대 3개 검수 행사 목록에서 당일 운영, 검수 유효성, 하선 후 예상 이동시간 30분 이하, 운항·입장·관람 조건을 검사한다.
5. POSSIBLE 후보만 실제 확보 수대로 공개한다. 카드에는 추천 이유·일정·이동수단/예상시간·위치·운영조건·알려진 요금·출처·수집/검수 시각을 표시한다. 요금은 선택 필터가 아니다.
6. 일정 충돌 시 같은 배편의 다른 검수 행사를 먼저 찾고, 없으면 오늘의 아직 출발하지 않은 이전 회차를 별도 변경안으로 제시한다. 변경안도 모든 조건을 통과해야 한다.
7. 적격 후보가 없으면 ‘오늘 조건에 맞는 검수 전시가 없습니다’와 일반적인 제외 사유를 표시한다. 조건부 카드·미검수 행사·과거 행사로 채우지 않는다. API/DB 장애로 조회할 수 없는 경우는 이용 불가로 구분한다.

총시간 안내: “배 출발부터 관람 종료까지 배 이동·하선 후 이동·대기·관람을 포함하며 귀가는 제외합니다. 하선 후 행사장까지의 예상 이동은 30분 이내인 경우만 안내합니다.”

| FR-19  | 검수 데이터 관리                   | 소수 행사와 이동경로의 근거·검수일·적용 범위·상태·버전 보관. 근거 변경 시 재검수.                                                                                                                           |

## 6. 데이터와 일정 판단 원칙

### 6.1 시간표 데이터

기존 시간표 JSON과 원본 자료를 재사용한다. 이전 문서의 준비 기록은 8개 선착장 ID, 34개 계산 조합, 예상값 300건, 원문 시각 140개·빈칸 52개다. 이는 당시 데이터 준비·계산 기록이며 현재 운항 여부나 제품 지원 범위의 증거가 아니다. 기존에 언급된 7개 선착장 목록과 데이터의 8개 ID 차이도 실제 구간 선정 때 확인한다.

- 도착예정은 선택한 출발 시각에 구간별 소요시간을 합산한다. 중간 선착장의 출발시각·빈칸으로 같은 항차를 추론하지 않는다.
- 원문 출발 시각이 없으면 선택 항목을 만들지 않는다. 환승·미지원 직항 조합은 허용하지 않는다.
- 공식 도착 열은 별도로 보존한다. 계산값을 공식 도착 시각·실시간 도착으로 표현하지 않는다.
- 회차 키는 로컬 데이터 참조이며 공식 항차 번호가 아니다.
- 실제 서비스 날짜의 운항 여부·예외·시간표 적용 기간을 검수한다. 확인되지 않으면 전체 여정의 불확실성에 반영한다.
- 날짜와 시각은 Asia/Seoul을 기준으로 함께 처리하고 자정 경계를 보존한다. 오늘 이미 출발한 배편은 대안으로 제시하지 않는다.

### 6.2 문화행사 원천과 수집

서울열린데이터광장 「서울시 문화행사 정보」를 기본 원천으로 사용한다. 공식 설명은 행사명·분류·기간·장소·위치·요금·행사시간 등의 제공과 매일 1회 갱신을 안내한다. 모든 행사에 모든 값이 채워져 있거나 예약 상태·입장 마감까지 제공된다는 뜻은 아니다.

기존 PRD의 보존 대상은 `TITLE`, `CODENAME`, `STRTDATE`, `END_DATE`, `DATE`, `PRO_TIME`, `PLACE`, `LAT`, `LOT`, `IS_FREE`, `USE_FEE`, `PROGRAM`, `ETC_DESC`, `ORG_LINK`, `HMPG_ADDR`, `MAIN_IMG`다. 실제 서비스명·인증 호출·필드 존재·좌표 정의는 샘플로 검증해야 한다. 필드 이름만으로 위경도 매핑을 확정하지 않는다.

수집은 사용자 요청과 분리해 **매일 09:00(Asia/Seoul)** 한 번 수행한다. 원천 API의 제공자 측 실제 갱신 완료 시각은 아직 미확인이다. 모든 페이지와 건수·필수 구조를 확인한 후 성공 스냅샷을 확정한다. 실패한 일부 페이지만으로 기존 성공본을 덮어쓰지 않는다. 원문·수집시각·스키마 버전·정규화 버전·오류를 보관하고, 요청 실행은 사용한 스냅샷을 고정한다.

정상 수집 0건, 필터 결과 0건, API 실패, 성공 수집본 없음은 별도 상태다. 안정적인 공식 ID가 없다면 행사명만으로 동일성을 판단하지 않고 검증 가능한 식별·중복 조정 규칙을 하위 데이터 명세에 정의한다.

### 6.3 소수 후보 직접 검수

지원 구간은 당일 조회에 사용할 전시 2\~3개의 운영·이동 근거를 검수할 수 있는 곳으로 조사 후 확정한다. 운영 검수 목록은 최대 3개이며 당일마다 유효성을 확인한다. 시연은 실행 당일 조회에 집중하고 날짜를 과거로 돌려 후보를 확보하지 않는다. 문서의 마곡→여의도 예시는 구간 결정이 아니다. **회의 조사 후보인 ‘야외 조각전’은 아직 운영 검수 목록의 유효한 추천 건으로 확정되지 않았다.** 행사 API 등록, 오늘의 전시 유지 여부, 실제 입구와 이동수단/분·운영시간·입장 조건·출처/확인일을 확인해야 한다. 11월 14일을 발표일인 11월 9일의 당일 조회 결과처럼 사용하지 않는다.

검수 기록에는 다음을 포함한다.

| **대상**  | **반드시 남길 근거**                                              |
| ------- | ---------------------------------------------------------- |
| 선착장·행사장 | 좌표·입구 위치·권역·출처·검수일                                         |
| 행사 조건   | 행사 ID/버전, 적용 날짜·회차, 운영시간·휴관·입장 마감·요금·예약 조건의 출처와 발췌         |
| 이동      | 선착장 하선 지점/출구→행사장 입구, 이동 방식·경로, 예상 소요시간, 자료/지도 링크·확인일·적용 범위 |
| 관람      | 정해진 공연 길이 또는 검수한 전시 관람시간과 그 근거. 별도 희망 체류시간 입력은 현재 범위에 없음   |
| 검수 상태   | 검수자·검수시각·유효기간 또는 재검수 조건·누락/충돌 사항                           |

이동시간은 확인한 자료에 기반한 **예상값**이다. 개인별 보행 속도·현장 대기·접근성을 보장하지 않는다. 직선거리를 속도로 나누어 검수된 실제 도보시간처럼 사용하지 않는다. 근거 없는 하선·이동 여유시간을 몰래 더하거나 0으로 처리하지 않고, 계산 가정은 공개한다.

원천이 바뀌었거나 적용일이 맞지 않으면 기존 검수값을 자동 승계하지 않는다. 예약 필요 정보만 있고 사용자의 예약 확보 여부가 없으면 예약 완료로 판단하지 않는다. 출처 간 충돌은 운영자가 해결하기 전까지 UNKNOWN으로 다룬다.

### 6.4 당일·이동 30분·검수 필터

서버의 Asia/Seoul 날짜를 service_date로 사용하고 오늘 운영하는 검수 전시만 대상으로 한다. 행사 전체 기간에 포함돼도 휴관·운영시간·입장 마감을 별도로 검사한다. 날짜가 바뀌거나 선택 배편이 출발했으면 결과를 재검증한다.

하선 지점부터 행사장 입구까지 검수된 예상 이동시간이 30분 이하인 후보만 허용한다. 이동수단은 이번 결정에서 특정하지 않았으므로 검수 기록에 실제 수단·경로·포함 구간을 명시한다. 대기·환승이 있는 이동은 필요한 시간을 포함해 검수해야 하며 누락되면 제외한다. 직선거리에서 시간을 추측하지 않는다. 하선 소요시간이 이동값에 포함됐는지 구분해 중복 합산하지 않는다.

취향·분위기·유무료 선호·자유문 조건 입력을 제거한다. 요금은 원천 정보로 보존하지만 필터·개인화 점수에 사용하지 않는다. 단순 요금 누락은 ‘요금 미확인’으로 안내하며, 운영·이동·예약 등 방문 판단 필수 정보 누락과 구분한다. 무료라고 추정하지 않는다.

표시 순서는 코드의 일정 적합성 검사 후 예상 이동시간 오름차순, 동률이면 안정적인 행사 ID 순서를 초기안으로 한다. 개인 취향 적합도 순위로 표현하지 않는다. 총시간 예산은 선택형/숫자 입력이며 입력하지 않으면 90분을 임의 생성하지 않는다.

### 6.5 일정 계산

공통 기준:

```
예산 종료 = 선택한 배 출발일시 + 사용자 총시간 예산
행사 도착예정 = 계산된 배 도착예정 + 확인한 하선·이동 소요시간
최종 종료 한도 = 총시간 입력 시 예산 종료; 미입력 시 사용자 예산 한도 없음

```

총시간이 입력되지 않았다면 임의의 90분을 사용자 제약으로 생성하지 않는다. 운영조건 자체는 계속 확인한다. 배편 변경안은 총시간을 입력한 경우 같은 길이를 새 출발시각에 적용한다. 별도 종료일시·희망 체류시간은 현재 입력 범위에 없다. 총시간 미입력 시 예산 종료 비교를 생략하고 검수 관람시간과 폐장·입장 마감은 계속 검사한다.

| **행사 유형**      | **판단 규칙**                                                                              |
| -------------- | -------------------------------------------------------------------------------------- |
| 자유 입장 전시·체험    | 방문 시작=max(행사 도착예정, 개장). 입장 마감 이전인지 확인하고, 검수된 필요 관람시간을 더한 종료가 폐장·최종 종료 한도 이내인지 비교.      |
| 고정 시각 공연·예약 회차 | 도착이 해당 회차의 공식 입장 조건·시작시각에 맞는지 확인. 공연 종료/길이와 총시간을 비교. 늦게 도착한 시각부터 관람을 시작하는 산식으로 바꾸지 않음. |
| 유형·필수 조건 미상    | 확인 가능한 충돌만 판정. 부족한 조건을 명시하고 방문 가능을 확정하지 않음.                                            |

`END_DATE`는 행사 전체 종료일이며 매일 폐장시각이 아니다. 폐장과 입장 마감도 다르다. 조건이 적용되지 않음은 확인 근거가 있을 때만 사용하며 빈 필드를 적용 없음으로 간주하지 않는다.

### 6.6 방문 가능성과 최신성

| **상태**      | **기준**                                                                    |
| ----------- | ------------------------------------------------------------------------- |
| POSSIBLE    | 방문일 운항·이동·행사 유형별 필수 조건이 확인되고 수치 비교와 하드 제약을 통과. “확인한 자료와 예상시간 기준 가능”으로 표시. |
| CONDITIONAL | 필수 이동·운항·운영·예약 조건 등이 미확인인 내부 판정. 추천 카드와 변경안에서는 제외하고 누락 사유를 trace에 기록.     |
| IMPOSSIBLE  | 확인한 날짜·시간·하드 제약과 충돌. 요금은 표시 정보로만 사용. 충돌 이유와 근거를 보존하고 일반 추천 후보에서는 제외.      |

확인된 불가 조건은 다른 필드가 누락됐다는 이유로 조건부로 바꾸지 않는다. 운항일 UNKNOWN을 행사 카드 바깥에만 숨긴 채 전체 여정을 POSSIBLE로 표시하지 않는다.

최신성은 별도 `FRESH / STALE / UNAVAILABLE`로 관리한다. 세부 분류 권고안: 24시간 이내의 성공본이며 최신 예정 수집이 성공한 상태는 FRESH, 최신 수집이 실패해 허용 성공본으로 대체하는 상태는 STALE, 성공본 없음 또는 나이 24시간 초과는 UNAVAILABLE이다. 정확히 24시간은 허용한다. 요청 접수와 최종 공개 시점 모두 고정 성공본의 나이를 검사한다. 실행 중 24시간을 초과하면 DATA_UNAVAILABLE로 종료하며, 다른 스냅샷으로 조용히 교체하지 않는다. 저장 결과를 나중에 다시 조회할 때도 만료 결과를 현재 유효한 추천으로 표시하지 않는다. 최초 예정 수집 전 성공본은 유효기간 안이면 FRESH로 보며 마지막 수집 상태를 별도로 표시한다. 일일 수집 실패 시 DB가 정상이고 **마지막 성공 배치 완료로부터 24시간 이내**인 성공본만 사용한다. 보관은 최근 성공 스냅샷 2개까지 하되, 오래된 보관본이 존재한다는 이유로 24시간 제한을 늘리지 않는다. 매일 09:00 수집이 실패하면 직전 일자의 성공본이 24시간 이상 지나 곧 `UNAVAILABLE`이 될 수 있다. 최신성 한도를 넘었거나 성공본이 없으면 추천을 중단한다. 갱신주기가 하루 1회여도 당일 변경의 반영을 보장하지 않는다.

## 7. 멀티 에이전트와 LLM에 대한 제품 요구

### 7.1 필요한 협업

최소 3개의 구분되는 에이전트와 Critic 책임을 실제 실행으로 보여준다. 업무는 ① 선택 배편·이동계획의 근거 검토 및 대안 판단, ② 검수 행사 정보에 근거한 추천 이유 작성, ③ 일정·추천 결과의 의미 검토와 수정 요청이다. 취향 해석 제거 후에도 역할별 입력·허용 도구·판단·Handoff를 구분하며 단순 조회 함수를 에이전트 수로 세지 않는다.

일정 검토 역할에 Critic 책임을 결합하는 구조도 검토할 수 있다. 별도 검증기를 두더라도 코드 검사 모듈을 자동으로 LLM 에이전트 1개로 계산하지 않는다. 공식 가이드의 “3개 이상, Critic 포함”을 “도메인 3개+별도 Critic 반드시 추가”로 확대하지 않는다.

협업 구조는 응답속도·결정 일관성·장애 격리에 대한 선택 근거를 제시해야 한다. 최종 상태·재탐색·복구 적용·종료의 소유자는 하나로 정한다. 각 에이전트가 다른 에이전트를 무제한 재귀 호출하지 않는다.

### 7.2 LLM과 코드의 역할

| **LLM에 맡길 판단·해석**        | **코드가 보장할 처리**                         |
| ------------------------ | -------------------------------------- |
| 선택 배편·이동 근거 검토와 대안 설명    | 구조화 입력·타입·허용 ID·권한 검사                  |
| 원문에 있는 운영조건의 보조 추출       | 날짜·시간·거리 계산 및 결정적 충돌 판정                |
| 허용 후보의 일정·이동 근거 기반 추천 이유 | 스냅샷·후보 ID·출처·정규화 값 일치, 이동 30분·당일 조건 검사 |
| 검증 결과의 설명·허용 대안 요청       | 재시도·호출·시간·비용 한도, 상태 전이, 최종 저장          |
| 추천의 의미적 일관성 검토           | 미검증 출력 차단, 허용 도구만 실행                   |

코드는 임의 자연어의 모든 의미를 자동으로 증명할 수 없다. 필터 조건·가격·시각·행사 유형처럼 검증 가능한 주장과 이를 연결한 짧은 이유를 기본으로 하며, 근거 없는 분위기·품질·접근성 주장은 확정 문장에서 제거하거나 미확인으로 표시한다. Critic 검토를 거쳐도 사실성 100%를 주장하지 않는다.

LLM은 전체 원천을 무제한 읽지 않고 필터링된 후보를 사용한다. DB·도구 결과 안의 지시문은 데이터로 취급한다. 새 행사·좌표·시간·요금·URL을 만들거나 사용자 하드 제약을 바꾸지 않는다. LLM 장애 시 비구조화 문장을 그대로 공개하지 않는다.

### 7.3 Handoff·메모리·최종 검증 요구

다음 실행에 목적·입력 참조·사용자 제약·기대 출력·완료 단계·중간 결과·근거·실패 원인·시도 횟수·남은 예산을 누락 없이 전달한다. 실행/작업/전달 식별자와 송수신 주체, 스키마·데이터·모델·프롬프트 버전을 추적한다. 원문은 필요한 부분 또는 접근 가능한 참조로 전달한다.

기존 초안의 16개 필드 목록은 하위 계약 설계의 출발점이며 고정된 필드 개수 자체가 제품 요건은 아니다. 초기 단계에서 아직 없는 이동 계획·후보를 가짜 값으로 채우지 않도록 공통 필드와 단계별 필수값을 구분한다. `run_id`만으로 다수 작업·반복을 구분할 수 없다면 `task_id`·`step_id`를 추가한다.

Critic은 통과·수정 요청·중단 권고와 사유를 반환하고, 단일 조정 주체가 예산·제약을 적용해 다음 단계와 종료를 결정한다. 후보 조회 성공·JSON 형식 통과만으로 최종 성공을 선언하지 않는다. 최종 공개 결과와 필수 실행 기록의 저장이 완료되어야 성공을 반환한다.

### 7.4 협업 구현 기준과 런타임 제안

- **회의 채택 구현 방향:** Python과 LangGraph StateGraph로 이동 검토·문화행사 설명·일정 검토/Critic의 세 역할을 연결한다. 기존 코드와 의존성을 확인하고 설치·연결·실행 검증 결과를 기록한다. Python 세부 버전 제안과 LangGraph 채택 상태는 구분한다. 단순 노드 세 개 생성으로 에이전트 요건 충족을 주장하지 않는다.
- **설계 원칙:** Supervisor가 공유 상태·예산·전이·종료를 단일 소유한다. 에이전트는 다음 행동을 제안하며 코드가 허용 여부를 결정한다. 그래프 재귀 제한만으로 업무 예산을 대체하지 않는다.
- **설계 원칙:** LLM 공급자 호출을 교체 가능한 어댑터로 분리한다. 기존 OpenAI API 방향은 승계하며 특정 모델은 계정 사용 가능 여부·실호출·비용·지연 검증 후 정한다. 키와 비밀값은 프롬프트·공개 응답·로그에 포함하지 않는다.
- **현재 역할 적용:** 이동 에이전트는 계산된 이동계획·운항 근거의 검토와 허용 대안 판단, 행사 에이전트는 검수 후보의 추천 이유 작성, 일정/Critic은 일정·근거·설명 일관성 검토를 맡는다. 취향 해석·무료 필터·개인화 순위는 만들지 않는다.
- **검증 경계:** 코드가 당일·이동 30분·허용 목록 최대 3개·ID·스키마·산술을 검사한다. Critic은 의미 일관성을 검토한다. 코드 Validator·Recovery는 에이전트 수에 산입하지 않는다.
- **실행 기록:** 역할별 입력·도구·출력·Handoff·모델/프롬프트 버전·수정/거부 사유를 남긴다. 그래프 상태와 PostgreSQL에 저장된 실행 결과를 연결한다. 별도 체크포인트 저장소·추가 브로커 도입은 필수가 아니다.
- **연결 검증:** 제출 전 실제 LLM을 연결한 전체 정상 흐름을 최소 1회 확인한다. 이는 반복 mock 장애 시험을 대신하지 않는다. CI에서는 고정 응답과 mock을 사용하고 실제 연결 증거는 별도로 보관한다.

## 8. 결과·장애·복구 정책

### 8.1 상태 구분

하위 계약은 적어도 다음 네 축을 구분해야 한다. enum 명칭은 계약에서 확정하되 서로 다른 의미를 한 값으로 합치지 않는다.

| **축**     | **의미와 예시**                                             |
| --------- | ------------------------------------------------------ |
| 실행 상태     | 대기·실행 중·성공·기능 축소·실패·안전 중단                              |
| 추천 결과     | 적격 후보 있음, 적격 후보 없음, 데이터 이용 불가. 조건부는 공개 결과 종류로 사용하지 않음. |
| 후보 방문 가능성 | POSSIBLE, CONDITIONAL, IMPOSSIBLE                      |
| 데이터 최신성   | FRESH, STALE, UNAVAILABLE                              |

정상적으로 모든 조건을 확인했으나 행사가 0건인 것은 성공적으로 수행한 조회의 빈 결과다. 필수 정보 누락으로 내부 제외된 후보도 시스템 장애와 구분한다. 재탐색 횟수를 채운 뒤 적합 후보가 없는 경우는 후보 없음으로 정상 종료할 수 있다. 실행 deadline 초과·필수 데이터 미확보·필수 저장 실패·검증을 통과하지 못한 출력은 실패/중단 또는 명시적 기능 축소로 기록한다.

### 8.2 업무 대안 탐색

1. 원래 배편·오늘·도착지·이동 30분·총시간 제약을 유지하며 최대 3개 검수 목록 안에서 다른 전시를 찾는다.
2. 없으면 같은 지원 구간의 오늘 아직 출발하지 않은 이전 배편을 **제안**하고 이동 30분·전체 일정·총시간을 다시 검증한다.
3. 필수 조건이 미확인인 후보는 내부 제외하고 사용자 추천·변경안으로 제시하지 않는다.
4. 후보가 없으면 없음과 이유를 반환한다. 사용자가 선택을 바꾸기 전에는 원래 배편을 유지한다.

업무 대안 탐색과 일시 오류 재시도는 서로 다른 작업·카운터다. 이미 검사한 배편·행사·버전 조합을 이유 없이 반복하지 않는다. 오늘·총시간·이동 30분 제약과 도착 선착장을 자동 변경하지 않는다.

### 8.3 장애 대응

| **상황**             | **기대 동작**                                                                 | **복구 기록**                                          |
| ------------------ | ------------------------------------------------------------------------- | -------------------------------------------------- |
| LLM/API 일시 timeout | 제한 재시도 후 가능한 경우 같은 검증 후보의 기본 정보 제공                                        | 설명·검토 대체와 원 의존성 복구를 구분                             |
| LLM 형식 오류          | 스키마 차단→수정 요청 한도 적용→검증된 기본 정보 또는 중단                                        | 잘못된 출력 미노출, 실제 호출·수정 횟수                            |
| 에이전트 예외            | 안전한 단계만 한도 내 재실행, 지속 실패 종료·알림                                             | once/persistent 구분, 중복 저장 없음                       |
| 문화행사 수집 API 실패     | 부분 배치 공개 금지, DB의 허용된 최신 성공본 사용                                            | 실패 배치·사용 스냅샷·나이·대체 이유                              |
| 행사 성공본 없음/만료       | 데이터 이용 불가, 수집 상태 안내                                                       | 후보 없음과 구분                                          |
| 필수 데이터 UNKNOWN     | 해당 후보 추천 제외. 적격 후보가 없으면 정상 빈 결과                                           | 누락 원인과 근거를 내부 trace에 기록                            |
| Critic 거부          | 사유가 있는 수정만 허용, 예산 소진 시 안전 중단                                              | 거부 근거·수정 지시·최종 미노출                                 |
| DB 연결/필수 저장 실패     | D-13: DB 비정상 종료에 Docker 자동 기동 적용, API는 제한 재접속; 복구 전에는 이용 불가·Discord·독립 로그 | Docker 재시작 여부와 실제 조회·필수 저장·API 정상 회복, 수동 개입 여부를 구분 |

LLM 설명·검토가 실패하면 코드로 당일·이동 30분·필수 일정 조건을 검증한 동일 후보의 기본 정보만 기능 축소 상태로 제공한다. Critic의 명시적 거부나 필수 조건 미확인은 대체 경로로 우회하지 않는다.

DB가 정상일 때 저장된 행사 성공본을 사용하는 정책은 **문화행사 API 장애 대응**이다. DB 장애 시 로컬 캐시로 추천을 계속하는 정책이 아니다. DB 이용 불가 중에는 시간표가 읽히더라도 전체 서비스 성공으로 응답하지 않는다.

DB 외부 로그에는 요청/실행/장애 ID·단계·시각·재접속 시도·Docker 재시작 여부·알림 결과를 남긴다. Discord 실패도 기록한다. **DB 컨테이너 비정상 종료 자동 재시작은 D-13으로 채택**했다. Docker 자체의 재시작이 완료되어도 DB 준비 및 앱 재연결·조회·저장·응답이 회복되지 않으면 자동 복구 성공이 아니다. 운영자가 DB를 수동 재가동했다면 수동 복구로 집계한다. `docker compose stop db`는 의도적 중지로 `unless-stopped` 자동 복구 대상이 아니며, DB가 살아있지만 응답 없는 경우도 `healthcheck`만으로 재시작되지 않는다. FT-03 시험 주입 방식에 따라 자동 복구 또는 기존 A안의 안전한 중단·알림·수동 복원을 각각 검증하고 강사 기대 동작은 별도 확인한다.

### 8.3.1 PostgreSQL Docker 설정·복구 확인 예시 (채택 방향, 코드 적용 전)

```yaml
services:
  db:
    image: postgres:18  # 사용자 확정 메이저 버전; 배포 시 패치 버전 또는 digest 기록
    restart: unless-stopped
    environment:
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: ${POSTGRES_DB}
    volumes:
      - postgres_data:/var/lib/postgresql
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U $$POSTGRES_USER -d $$POSTGRES_DB"]
      interval: 10s
      timeout: 5s
      retries: 5

volumes:
  postgres_data:
```

공식 postgres:18 이미지의 기본 PGDATA는 `/var/lib/postgresql/18/docker`이며, 영속 Volume은 `/var/lib/postgresql`에 마운트한다. 기존 다른 메이저 버전의 데이터가 있으면 이미지 태그만 교체하지 않고 별도 데이터 이전 절차를 확인한다. 근거: [Docker 공식 PostgreSQL 이미지 문서](https://github.com/docker-library/docs/blob/master/postgres/content.md#pgdata "Docker 공식 PostgreSQL 이미지 문서").

위 예시는 **별도 DB 컨테이너와 영속 저장소, 자동 재시작, 상태 확인**을 표현한다. 실제 프로젝트의 기존 Compose를 지우거나 덮어쓰라는 지시가 아니다. `healthcheck`는 준비 상태 표시일 뿐 자체 자동 재가동 기능이 아니다. 운영 환경에 맞는 비밀값 관리, `api`·`worker`의 DB 재연결, 실제 복구 검증은 별도 구현해야 한다. `docker compose stop db`를 자동으로 되돌리려면 현재 채택 범위를 넘어서는 **독립 감시 주체**가 필요하며, Docker 제어 권한의 보안 위험까지 평가해야 한다.

### 8.4 운영 수치의 초기안과 확정 방법

다음 표의 `채택` 값은 이번 회의에서 선택된 **구현 운영 설정**이며 공식 과제 수치·이미 시험된 성능 수치는 아니다. `기존 유지`와 `미정`도 구분한다. 아키텍처/환경 설정에 단일 값으로 반영하고 실제 시험에서 한계를 검증한다.

| **항목**                         | **적용 값**                           | **상태·조건**                                                                                                |
| ------------------------------ | ---------------------------------- | -------------------------------------------------------------------------------------------------------- |
| 전체 요청 실행 한도                    | **90초**                            | 채택. 사용자 응답속도 성과 수치가 아님. 제한 초과 시 안전 중단.                                                                   |
| LLM 1회 timeout                 | **15초**                            | 채택. 남은 전체 시간보다 길게 대기하지 않음.                                                                               |
| 전체 LLM 호출 상한                   | **8회**                             | 채택. 모든 역할·대안 탐색·형식 수정·SDK 자체 재시도까지 합산. SDK 숨은 재시도 설정도 통제.                                                |
| 업무 재탐색 상한                      | 2라운드                               | 기존 제안 유지(확정 전). 기본 탐색 이후 추가 탐색. 중첩 루프 금지.                                                                |
| 외부 API/LLM 일시 오류 추가 재시도        | **최대 2회** (최초 포함 최대 3번)            | 채택. timeout/일시적 서버 오류 등에만 적용, 영구 오류 제외. 호출 사이 짧은 지연 및 전체 시간/호출 상한 적용.                                    |
| LLM 출력 형식 수정                   | **최대 1회**                          | 채택. 위 재시도와 별도 사유로 기록하되 전체 LLM 8회에 포함.                                                                    |
| DB 연결 재시도 횟수·기간                | 미정                                 | FT-03 기존 제한 재접속 유지. 외부 API 재시도 2회를 DB에 무단 적용하지 않음. 복구 중 DB 재연결/쓰기 중복 방지·총 90초 예산 반영.                     |

수집 API timeout, 최초 수집 실행 시각의 정확한 처리, 모델명·금액 상한, 세션/보관 정책의 세부 저장 위치, FT-03 DB 재접속 횟수·간격과 재시작 실패 경고 임계값은 담당자가 첫 통합 시험 전에 정한다. Docker 비정상 종료 자동 재시작 정책 자체는 D-13으로 확정되었다. 무제한을 기본값으로 두지 않으며 확정하지 않은 항목을 완료라고 기록하지 않는다. 특히 **09:00 수집 + 성공본 24시간** 조합에서 다음 날 09:00 수집이 실패하면 직전 성공본이 만료될 수 있다. 이는 사용자에게 `DATA_UNAVAILABLE`로 알리는 현행 PRD 정책을 따른다.

## 9. API·보안·운영 제약

### 9.1 API의 업무 경계

아래는 기능 진입점 기준안이다. 정확한 JSON Schema·HTTP 오류·비동기 구현 방식은 하위 API 명세로 확정한다.

| **진입점**                  | **책임**                                        |
| ------------------------ | --------------------------------------------- |
| `GET /api/stops`         | 선착장과 실제 지원 조합·표시 상태                           |
| `GET /api/trips`         | 날짜·지원 구간의 로컬 출발 항목, 계산 예상값·운항 확인 상태           |
| `GET /api/events`        | 코드 필터 후보·원문·신선도. 사용자 여정의 최종 승인과 구분            |
| `POST /api/itineraries`  | 오늘의 배편·선택적 총시간 기반 실행 접수와 run_id. 취향·무료 필터 없음. |
| `GET /api/runs/{run_id}` | 본인 실행의 진행·대안·검증 결과 조회                         |
| 운영 조회·health             | 권한 있는 실행/장애/수집 조회, 프로세스 생존과 DB·데이터 준비 구분      |

이번 회의에서는 FastAPI가 PostgreSQL에 실행 작업을 기록하고 별도 worker가 처리하는 방식을 채택한다. 요청 접수 시 비동기 `202`를 사용한다면 **요청·잡의 필수 저장에 성공한 후에만** 접수 완료로 응답한다. 중복 요청·재시작에 따른 중복 실행과 중복 완료를 방지한다. 이전 초안의 `POST /api/runs`를 별도 파이프라인으로 이중 구현하지 않는다. 실제 사용 클라이언트가 있을 때만 호환 필요성을 검토한다.

공개 결과에는 사용한 이동 정보, 행사 ID·버전·제목·분류·장소·거리 유형·기간/시간·요금·공식 링크, 추천 이유·근거·불확실성, 방문 가능성, 데이터 수집·검수 시각이 연결되어야 한다. 원문 전체·내부 연결정보·비밀값은 노출하지 않는다.

### 9.2 보안과 관측

- 비회원이라도 실행 결과의 세션 소유권을 검사한다. run_id를 안다는 이유만으로 조회를 허용하지 않는다.
- 운영 조회·장애 주입·수동 수집은 별도 권한 경로로 제공한다. 일반 서비스의 장애 주입 기능은 비활성화한다.
- DB 쿼리는 파라미터 바인딩을 사용한다. LLM에 임의 SQL·셸·배포·내부 URL·DB 관리 도구를 주지 않는다.
- 원문과 LLM 출력의 HTML을 그대로 실행하지 않는다. 외부 링크는 원천에서 검증한 공개 링크를 사용한다.
- DB·LLM·문화행사 API·Discord·AWS·SSH 비밀값은 서버/CI secret으로 관리한다. API 키가 경로에 있는 인증 URL도 로그에 남기지 않는다.
- 입력 길이·요청 빈도·동시 실행·호출/시간/비용 한도를 둔다. 무한 재시도·무한 알림을 막는다.
- 구조화 로그에 run/step/handoff ID, 오류 유형, 시도·대체·소요시간·수동 개입·데이터/모델/프롬프트 버전을 기록한다.
- 실행 상태와 최소 운영 지표는 확인 가능해야 한다. 별도의 대규모 모니터링 제품 도입은 필수가 아니다.

### 9.3 운영 구현 기준

이번 개정은 v0.9.1.1 전체 요구를 승계하고 대시보드·로그의 구현 기준을 보완한다. 아래 신규 세부 설계는 \*\*개정 권고안(팀 확인·구현 전)\*\*이다. 기존 채택값은 유지하며, 완료 증거를 새로 주장하지 않는다.

운영 수치는 8.4의 채택값을 따른다. 과거 제안과의 비교는 부록 B에 기록한다.

**기술 선택 권고:** Auto Healing은 기존 LangGraph 흐름의 명시적 오류 분기와 코드 기반 Recovery Controller로 수행한다. 실제 LLM 호출·남은 시간·재시도 횟수를 공통 실행 상태에서 통제하고, 복구 조치는 허용 목록으로 제한한다. DB 컨테이너 재시작은 Docker에 맡긴다. LLM이 임의 명령이나 Docker 소켓을 사용하는 구조로 확대하지 않는다.

로그는 Python 표준 logging의 JSON formatter로 구조화하고, **PostgreSQL 조회용 이력 + DB와 독립된 영속 JSONL**을 사용하도록 권고한다. FastAPI가 운영 조회 API를 제공하고 기존 React·TypeScript의 /admin 화면이 조회한다. 현 프로젝트 규모에서는 별도 로그 서버를 필수 구성으로 추가할 필요가 없다. 향후 로그량·검색 요구가 커지면 전용 수집·검색 체계를 별도 검토한다.

### 9.4 운영 대시보드 네 영역

| **영역**   | **권고안 채택 시 필수 표시**                                                                     | **운영자가 판단할 내용**             |
| -------- | -------------------------------------------------------------------------------------- | --------------------------- |
| 전체 상태    | API 생존, DB 준비, worker 최근 heartbeat, 수집 마지막 결과 및 확인 시각; 당일 접수·대기·진행·성공·기능 축소·실패·안전 중단 수 | 서비스가 응답 가능한지, 작업이 정체됐는지     |
| 실행 이력    | run_id, 시작/완료 시각, 단계·에이전트, 단계별 소요시간, 실제 LLM 호출 수, 최종 실행 상태, 추천 결과 유형·후보 수, 오류 요약       | 특정 요청이 어디서 지연·실패했는지         |
| 장애·복구 이력 | incident_id, 오류 유형, 감지 시각, 영향 단계, 시도 횟수, 복구 조치, 검증 결과, 자동/대체/수동/미복구, 알림 전송 상태          | 어떤 조치로 복구됐으며 사람의 개입이 있었는지   |
| 데이터 상태   | 마지막 수집 시도·성공 시각, 데이터 나이·24시간 만료 여부, 수집 전체·검수 완료·당일 적격 수, 제외 사유별 수, 사용 스냅샷 ID           | 후보가 적은 이유가 정상 조건인지 데이터 장애인지 |

추천 후보 0건은 정상 NO_MATCH일 수 있으므로 오류로 집계하지 않는다. 데이터 상태의 당일 적격 수는 선택 배편과 구간에 따라 달라지므로 조회 조건을 함께 표시한다. CPU·메모리·토큰 차트는 선택 사항이다.

상태 집계는 접수 시각이 선택 기간에 속하는 고유 run_id를 대상으로 한다. 접수 수는 대기·진행 및 최종 상태별 수의 합과 일치해야 하며 마지막 집계 시각을 표시한다. worker heartbeat 지연 기준은 설정으로 명시하고, 관측 실패를 정상 상태로 표시하지 않는다.

**요청 예산 계약 권고:** accepted_at은 필수 작업 저장에 성공한 접수 시각, execution_started_at은 worker 시작 시각이다. deadline_at=accepted_at+90초로 정해 대기·재시도·재시작 후 재개에도 유지한다. 만료된 대기 작업은 실행하지 않고 안전 중단으로 기록한다. 90초 수치는 변경하지 않으며, 이 시작점 상세는 팀 확인 전 권고안이다.

기본 조회는 KST 당일, 자동 갱신은 10초와 수동 새로고침을 권고한다. 기간·상태·오류 유형·실제 운영/시험 필터, 실행 상세→단계→장애 상세 연결을 제공한다. 기본은 **조회 전용**이며 수동 수집 버튼은 후속 선택 사항이다.

### 9.5 로그 저장·전달과 장애 중 조회

- 공통 event_id를 가진 구조화 이벤트를 API와 worker에서 생성한다. 프로세스별 JSONL 파일을 영속 마운트에 기록하고 PostgreSQL 이력으로 적재한다. 다중 프로세스가 하나의 회전 파일을 경쟁적으로 쓰지 않도록 파일을 분리한다.
- DB 장애 시에도 JSONL에 기록한다. 재연결 뒤 event_id의 유일성 제약으로 중복을 제거하며 재적재한다. 재적재 위치를 기록하고, 완료 전인 로그를 이미 DB에 저장한 것으로 표시하지 않는다. 원본 이벤트와 요약 상태 갱신을 분리하고, 실행·장애별 상태 버전으로 오래된 이벤트가 최신·종료 상태를 덮어쓰지 못하게 한다. 재적재 커서는 DB 트랜잭션 커밋 후에만 전진시킨다.
- JSONL도 기록하지 못하면 stderr와 운영 알림에 기록 실패를 남긴다. DB 독립 저장은 EC2 자체 장애까지 견디는 고가용성 저장을 뜻하지 않는다.
- 운영 API는 PostgreSQL을 주 조회원으로 사용한다. DB 중단 시 이력 화면에는 **이력 조회 불가**, 마지막 성공 조회 시각을 표시한다. 0건·정상으로 대체하지 않는다. JSONL을 브라우저에 직접 공개하지 않고 운영자가 서버에서 확인한다.
- DB 로그와 JSONL은 7일 보존을 적용한다. 순환 정책·용량 한도를 설정하고 미전송 기록 손실 시 누락을 표시한다. FT 원자료는 만료 전 제출 증빙으로 별도 보존한다.
- 원문 프롬프트·응답 전문은 기본 저장하지 않는다. 오류 메시지·URL을 정제하고 비밀값·세션 토큰·개인정보는 제거한다. 근거 ID·버전·검증 결과 중심으로 저장한다.
